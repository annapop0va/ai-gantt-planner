# AI Gantt Planner

MVP-планировщик проектов: вы загружаете план из Excel, получаете интерактивную диаграмму Ганта, редактируете план обычным языком через AI-ассистента и экспортируете обновлённый план обратно в Excel. Выполнено как тестовое задание для Biocad.

## Демо

**Приложение:** https://ai-gantt-planner-2.onrender.com
**Backend API:** https://ai-gantt-planner-1-7a0r.onrender.com (`/api/v1/health`)

Оба сервиса развёрнуты на бесплатном тарифе Render. Backend может «засыпать» после периода неактивности — первый запрос после этого может выполняться до минуты. Frontend в этот момент показывает экран «Запускаем сервер…» и автоматически повторяет попытки подключения (см. раздел [Ограничения MVP](#ограничения-mvp)).

## Возможности

- Импортирует план проекта из Excel (задачи, исполнители, длительности, зависимости) и строит по нему диаграмму Ганта.
- Позволяет редактировать план обычным языком через панель AI-чата.
- После каждого изменения детерминированно пересчитывает даты и зависимые задачи — LLM никогда не вычисляет даты самостоятельно.
- Применяет составной запрос как одно атомарное изменение либо отклоняет его или запрашивает уточнение — вместо того чтобы угадывать.
- Экспортирует текущий (в том числе изменённый) план обратно в Excel.
- Включает dev-only mock-режим с 12 фиксированными UI-состояниями для проверки frontend без backend.

## Сценарий демонстрации

1. Откройте приложение и перетащите [`examples/sample_patient_card_project.xlsx`](examples/sample_patient_card_project.xlsx) на экран импорта (или скачайте его по ссылке «Скачать пример Excel» на этом экране).
2. Нажмите «Построить план» — выполняется реальный импорт через backend, и строится канонический план из 16 задач (старт 07.09.2026, релиз 02.11.2026) в виде диаграммы Ганта.
3. Отправьте в чате AI-команду, например:

   > Согласование требований к карточке пациента и расписанию врача займёт на 2 рабочих дня больше. Увеличь Frontend-разработку карточки пациента до 8 рабочих дней. После Согласования результата разработки добавь две параллельные задачи: «Правки backend по итогам согласования» на 2 рабочих дня для Василия и «Правки frontend по итогам согласования» на 3 рабочих дня для Дмитрия. QA-тестирование карточки пациента должно начинаться после завершения обеих задач.

4. Agent через MCP находит нужные задачи и применяет одно атомарное ChangeSet; диаграмма Ганта и чат обновляются на основе diff, посчитанного backend'ом: 18 задач, релиз сдвигается на 09.11.2026, две новые задачи идут параллельно после «Согласование результата разработки», а QA теперь зависит от обеих.
5. Экспортируйте обновлённый план обратно в Excel из панели инструментов.

## Архитектура

```
Browser ──► React (Vite) ──► FastAPI ──► Agent ──► MCP ──► ProjectService ──► Scheduler / InMemoryProjectStore
                                           │
                                           ▼
                                      OpenRouter (LLM)
```

**Backend — единственный source of truth.** LLM только предлагает вызовы MCP tools (прочитать план, найти задачу, предложить ChangeSet) — он никогда не вычисляет даты, никогда не пишет в проект напрямую и никогда не видит ни базу данных, ни файл. Любое изменение — вызвано оно AI-чатом или dev-only ChangeSet endpoint'ом backend — проходит через один и тот же `ProjectService.apply_change_set()`, где и живут детерминированный Scheduler и вся валидация.

## Зачем здесь MCP

MCP здесь — реальная граница, а не декоративный слой. Единственный способ для Agent прочитать или изменить проект — это ровно четыре allow-listed MCP tools: `get_project_outline`, `search_tasks`, `get_task_details`, `apply_change_set`. Видимая для модели схема каждого tool никогда не включает `project_id` или `expected_revision` — они привязываются на стороне сервера для каждого запроса, поэтому модель не может обратиться к другому проекту или обойти проверку revision, даже если попытается. Другого пути из Agent в проект просто не существует.

## Надёжность и консистентность

- **Deterministic Scheduler** — все даты, расчёт рабочих дней и пересчёт зависимых задач выполняет код backend, а не LLM.
- **Atomic ChangeSet** — операции внутри одного change set применяются либо все вместе, либо не применяются вовсе.
- **Optimistic concurrency через revision** — каждое изменение содержит `expected_revision`; устаревший запрос отклоняется, а не молча перезаписывает данные.
- **Не более одной успешной mutation за один AI-запрос** — даже составной, многочастный запрос превращается ровно в один атомарный вызов `apply_change_set`.
- **Уточнение вместо угадывания** — неоднозначная ссылка на задачу (например, совпадающая сразу с несколькими задачами) приводит к ответу `clarification_required` без каких-либо изменений. Это обеспечивается детерминированной проверкой на стороне сервера, а не оставлено на совесть модели.
- **Никакого automatic retry для mutations** — health-check и read-only GET-запросы можно безопасно повторять; `POST /chat`, импорт и `apply_change_set` — никогда, чтобы запрос не мог быть применён дважды.

## Локальный запуск

### Backend (Windows / PowerShell)

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
copy .env.example .env
python -m uvicorn app.main:app --reload --port 8000
```

Health-check: `http://localhost:8000/api/v1/health` → `{"status": "ok"}`. Интерактивная документация API: `http://localhost:8000/docs`.

Чтобы включить реальный AI-чат, добавьте в `backend/.env`:

```env
OPENROUTER_API_KEY=<your-openrouter-key>
OPENROUTER_MODEL=<a model id that supports tool/function calling>
```

Никогда не коммитьте реальный ключ. Без этих двух переменных всё, кроме `POST /chat`, работает как обычно; чат возвращает `503 AI_NOT_CONFIGURED`.

### Frontend

```powershell
cd frontend
npm install
npm run dev
```

Открывается на `http://localhost:5173` и обращается к backend по адресу `VITE_API_BASE_URL` (по умолчанию `http://localhost:8000`; переопределяется в `frontend/.env.local`).

## Переменные окружения

| Переменная | Где | По умолчанию | Назначение |
|---|---|---|---|
| `VITE_API_BASE_URL` | frontend | `http://localhost:8000` | Базовый URL backend, который вызывает frontend |
| `OPENROUTER_API_KEY` | backend | не задан | API-ключ OpenRouter; без него чат возвращает `AI_NOT_CONFIGURED` |
| `OPENROUTER_MODEL` | backend | не задан | Идентификатор модели — должна поддерживать tool/function calling, не задаётся жёстко в коде |
| `ENABLE_MCP` | backend | `true` | Подключает MCP-сервер по пути `/mcp` |
| `ENABLE_DEV_ENDPOINTS` | backend | `false` | Включает dev-only endpoint `POST /projects/{id}/changes` |
| `AGENT_MAX_STEPS` | backend | `6` | Максимум шагов agent loop за один запрос в чат |
| `AGENT_MAX_READ_TOOL_CALLS` | backend | `8` | Максимум read-tool вызовов MCP за один запрос в чат |
| `FRONTEND_ORIGINS` | backend | `http://localhost:5173` | Разрешённые origin'ы для CORS |

Полный список переменных, включая настройки таймаутов запросов и длины истории, — в `backend/.env.example` и `frontend/.env.example`.

## Ограничения MVP

- **Хранение проектов только в памяти, без базы данных.** Перезапуск backend или «засыпание» на бесплатном тарифе Render уничтожает все проекты и историю чата. Frontend отслеживает эту ситуацию (устаревший `project_id` → `PROJECT_NOT_FOUND`) и возвращает пользователя на экран импорта с понятным объяснением, а не молча падает.
- **Только Excel (.xlsx)** для импорта и экспорта.
- **Календарь — понедельник–пятница, 8 часов в день, без учёта праздников.**
- **Один исполнитель на задачу.**
- **Длительность — только целыми рабочими днями**, без учёта дробных дней.
- **Cold start на бесплатном тарифе Render** — публичный backend может «просыпаться» после неактивности до минуты.
- **Нет аутентификации, изоляции между пользователями и сохранения данных** между перезапусками.

## Как я проектировала и разрабатывала проект с AI

Дальше — не про то, что «AI помог ускорить разработку», а про то, как я выстроила процесс: что проектировалось до кода, как я ставила задачи AI-инструментам и на каких этапах возвращалась к проектированию, обнаружив небезопасное поведение.

### Почему я выбрала именно такой demo-кейс

Я старалась не делать тестовое просто ради формального выполнения. Вместо абстрактного Gantt вида «Задача 1 → Задача 2 → Задача 3» я взяла сценарий, структурно близкий к работе другой реальной продуктовой команды, где я в том числе занимаюсь функциональностью голосового AI-помощника: discovery → согласование требований → продуктовый дизайн → backend/frontend-разработка → согласование результата → QA. Роли и структура команды в demo Excel основаны на реальной рабочей команде — без клиента, работодателя и коммерческих деталей.

Так тестовое не стало одноразовым искусственным примером: сценарий позволил одновременно проверять зависимости, Scheduler, UX диаграммы Ганта и AI-изменения — и оценивать продукт не только как автор, но и как пользователь, который реально планирует delivery.

### Проектирование до coding и постановка задач для coding-agent

Работа не начиналась с команды «сделай мне AI Gantt Planner». Решение несколько раз проектировалось и уточнялось совместно с ChatGPT (модель GPT-5.6 Sol; для сложных этапов — режим Pro / deep reasoning): исходное тестовое → декомпозиция → product requirements → пользовательский сценарий → MVP scope → domain-правила → архитектура → corner cases → acceptance criteria → детальный implementation-промпт → реализация. Требования пересматривались несколько раз до основного кода. Заранее проектировались продукт (сценарий, ценность MVP, canonical demo, scope), domain-правила и архитектурные инварианты — большинство уже описаны выше, в разделах «Архитектура» и «Надёжность и консистентность» — а также сценарии сбоя AI: неоднозначность, hallucination, повторная mutation, stale revision, невалидный составной запрос, ошибки tool calling, потеря in-memory состояния. Deep reasoning нужен был не ради длинных ответов, а чтобы разобрать corner cases до кода и сократить число дорогих переделок архитектуры позже.

После проектирования я не передавала coding-agent команды вроде «сделай backend» или «сделай frontend». Для крупных изменений я формировала подробные implementation-промпты: контекст архитектуры, цель изменения, инварианты, разрешённые изменения, ожидаемое поведение и поведение при сбое, acceptance criteria, команды build/test, иногда — запрет commit/push до моей проверки. Без такого контекста coding-agent может незаметно сломать работающую архитектуру — я давала не инструкцию, а контракт изменения, управляя не только промптом, но и границами задачи.

### Переход между AI-сессиями и перенос контекста

После исчерпания доступного лимита основной AI-сессии я продолжила работу в другой сессии с доступным платным лимитом. Поскольку требования, архитектура, ограничения и acceptance criteria уже были формализованы, я перенесла этот контекст — с зависимостями между компонентами и тем, что менять нельзя — и продолжила разработку без перепроектирования.

Вывод: при работе с AI важно управлять не только промптом, но и переносимостью контекста между сессиями и инструментами.

### Frontend, дизайн и технический workflow

Frontend и дизайн создавались и итерационно дорабатывались тем же Claude Code, а не принимались после первой генерации — мне было важно получить не просто работающий backend, а сценарий, которым можно пользоваться без объяснения от разработчика.

Работа велась не только в браузерном чате: следуя AI-инструкциям, я сама прошла локальный workflow разработки и деплоя — VS Code с терминалом, Windows PowerShell и местами Git Bash, Git и GitHub, Python и virtual environment, Node.js/npm, Vite, OpenRouter API, Render. При debugging я передавала AI реальный runtime-контекст — терминальный вывод, логи Render, ошибки build, конфигурацию — и подход был одинаковым: сначала локализовать слой проблемы, потом проверять следующую гипотезу.

### Четыре показательных случая по дороге

**1. `.gitignore` и чистая production-сборка.** Локально `frontend/src/lib` существовал, но сборка на Render его не видела: причина — слишком широкое правило `lib/` в корневом `.gitignore`. Исправление — сузить до `/lib/`, файлы вернулись в Git. Вывод: «работает локально» не равно «репозиторий воспроизводимо собирается с нуля».

**2. Неоднозначная AI-команда.** Формулировка «перенеси разработку» могла затронуть сразу две похожие задачи — технически AI выполнял запрос, но продуктово это было небезопасно. Решение — deterministic ambiguity guard на backend: повторная проверка вернула `clarification_required` без mutation. Вывод: лучше переспросить, чем уверенно изменить не ту задачу.

**3. OpenRouter в публичном runtime.** После деплоя AI-чат не работал из-за runtime-конфигурации — по сообщению об ошибке проблема оказалась в `OPENROUTER_API_KEY` в environment на Render. После настройки публичный AI-flow заработал полностью. Вывод: debugging AI-продукта — это не только код, но и конфигурация provider/runtime/deployment.

**4. Render Free и `InMemoryProjectStore`.** Я подумала, что будет, если проверяющий откроет ссылку через несколько часов: бесплатный Render может «уснуть» — живая проверка подтвердила cold start порядка десятков секунд. Frontend получил health-check, состояние «Запускаем сервер…», ограниченный retry/backoff и Retry без автоповтора mutation. `InMemoryProjectStore` также теряет состояние после restart — вместо базы данных я решила корректно обработать устаревший `project_id`: очистить сессию, вернуть на импорт, показать понятное сообщение вместо raw 404. Persistence важна для продакшена, но не для этого тестового — для MVP разумнее сохранить scope и сделать аккуратный UX.

### Human-in-the-loop

AI-результат не принимался автоматически. За мной оставались: постановка задачи, выбор demo-кейса, продуктовые и архитектурные решения, acceptance criteria, принятие/отклонение AI-решений, проверка build и тестов, live end-to-end, деплой и финальное решение о готовности. Случай с неоднозначной командой — прямое доказательство: AI технически выполнил запрос, но я признала результат небезопасным и вернулась к проектированию. AI ускорял анализ, реализацию и debugging, но не заменял принятие решений.

## Что я вынесла из разработки

### Что в подходе сработало хорошо

1. **Раннее разделение LLM и бизнес-логики.** Deterministic Scheduler, ChangeSet, ProjectService и MCP-граница позволили менять модели и AI-инструменты, не трогая правила планирования проекта.
2. **Реальный canonical scenario.** Он одновременно стал demo, acceptance-тестом, backend-тестом, live LLM-тестом и UI-проверкой — с конкретным результатом: 16 → 18 задач, 02.11.2026 → 09.11.2026.
3. **Сознательное ограничение MVP** — только Finish-to-Start, один исполнитель, целые рабочие дни, in-memory store. Это не давало раздувать scope и позволяло сосредоточиться на главной цепочке: Excel → AI-изменение → детерминированный пересчёт → диаграмма Ганта → экспорт.

### Где я потеряла больше времени, чем было необходимо

Основные потери были не в core-бизнес-логике, а в порядке разработки и в том, что я поздно посмотрела на production-окружение. High-fidelity frontend и mock-состояния появились раньше полного real server flow. Чистая сборка из git checkout и первый полноценный деплой были проверены довольно поздно, поэтому infrastructure-specific проблемы (см. случаи выше) проявились уже ближе к финалу. По итогам стало понятно, где следующий цикл можно сделать быстрее и предсказуемее.

### Что я бы сделала иначе во второй итерации

Первое — я бы начинала не с frontend и backend как двух больших отдельных блоков, а сначала зафиксировала контракты: формат Excel, domain-модель, правила расчёта расписания, ChangeSet, API, MCP tools, ожидаемый результат канонической команды. После этого собрала бы минимальный сквозной сценарий от загрузки Excel до реального AI-изменения — простой backend, Scheduler, простой frontend, AI-команда, mutation, обновлённый план — и только потом переходила бы к high-fidelity диаграмме Ганта и UI. Такой порядок позволяет раньше проверить самые дорогие архитектурные предположения: ошибку в API или domain-модели дешевле исправить до того, как поверх неё построен детальный интерфейс.

Второе — я бы значительно раньше настроила чистую сборку и первый публичный деплой. Локальная среда не показывает целый класс проблем: hosting-дефолты, версию Python, Root Directory, environment-переменные, CORS, чистоту git-репозитория, cold start. Первый деплой я бы делала сразу после минимально работающего end-to-end сценария и раньше ввела бы регулярную проверку: fresh checkout → install → build → тесты → запуск.

Третье — я бы с самого начала проверяла негативные AI-сценарии одновременно с успешным. В acceptance criteria сразу вошли бы: неоднозначность, несуществующая задача, stale revision, невалидная операция внутри составного запроса, повторная mutation, сбой LLM/tool calling. Для AI-продукта, который меняет пользовательские данные, недостаточно проверить, что модель умеет выполнить правильную команду — не менее важно проверить, что система безопасно ведёт себя, когда уверенности недостаточно. Ambiguity guard, описанный выше, — конкретное доказательство этого вывода.

Четвёртое — я бы заранее поддерживала небольшой переносимый AI-контекст: текущая архитектура, зафиксированные решения, инварианты, статус, известные проблемы, следующая задача. В этом проекте после исчерпания лимита основного аккаунта работу пришлось продолжить в другой AI-сессии — это получилось без перепроектирования, потому что требования, архитектура и acceptance criteria уже были формализованы. Но заранее подготовленный контекст сделал бы смену аккаунта, модели или coding-agent ещё безопаснее и быстрее. Главный вывод: при работе с AI нужно управлять не только промптами, но и переносимостью контекста проекта.

### Что я бы сознательно оставила без изменений

- **`InMemoryProjectStore` для MVP** — PostgreSQL увеличил бы scope, но почти не усилил бы проверку главной продуктовой гипотезы.
- **Deterministic Scheduler** — LLM-based scheduling был бы менее воспроизводимым и тестируемым.
- **Finish-to-Start, один исполнитель, целые рабочие дни** — этого достаточно для canonical MVP-сценария.
- **MCP как граница** — она даёт контролируемое разделение между моделью и изменением domain-данных.
- **Render Free для demo** — тариф достаточен для тестового задания, если cold start корректно обработан на фронтенде.

### Главный вывод

Если бы я запускала проект снова, я бы не пыталась просто быстрее писать код. Я бы раньше проверяла ключевые предположения: реальный пользовательский сценарий, контракты, минимальный end-to-end, деплой, негативные AI-сценарии. При этом основные архитектурные решения я считаю удачными и повторила бы их снова.

Главный вывод этого проекта для меня в том, что скорость AI-assisted разработки определяется не скоростью генерации кода, а качеством постановки задачи, контекста, ограничений и проверки результата.

Подробная, по каждой задаче, запись о том, что было делегировано, что проверено вручную и что было исправлено, — в [`docs/ai-development-log.md`](docs/ai-development-log.md).
