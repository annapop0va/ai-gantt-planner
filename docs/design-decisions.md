# Design Decisions — High-Fidelity UX/UI

Этот документ фиксирует **почему**, а не **что** — предметно решения, которые нельзя однозначно вывести из кода, и компромиссы, принятые для этапа high-fidelity prototype.

## 1. Почему Gantt доминирует над Chat

Product-spec (§1) формулирует ключевой принцип: «LLM интерпретирует намерение пользователя. Backend контролирует данные». Из этого прямо следует UX-иерархия: **проектный план — главный объект интерфейса, чат — способ им управлять**, а не отдельная фича рядом с ним.

Практически это выражено так:
- пропорция 72% / 28% (Gantt / Chat), ширина чата зажата `min 340px / max 460px`, чтобы он не расползался на широких экранах и не отвлекал от плана;
- у чата нет собственного «фирменного» визуального языка (никакого gradient-фона, декоративных иллюстраций) — он оформлен как обычная рабочая панель, визуально младше Gantt;
- результат AI-команды (`ChangeSummary`) показывается **и** в чате, **и** на самом Gantt (легенда + маркеры + подсветка бара) — так подтверждение изменения не требует переключения внимания между двумя разными «мирами» интерфейса.

## 2. Почему light theme

Задание явно требует light theme, но решение имеет и продуктовое обоснование: это **рабочий инструмент для длительного использования** (PM держит его открытым весь день, рядом с таблицами, почтой, календарём). Тёмная тема хороша для creative/monitoring-инструментов с низкой информационной плотностью; для плотной таблицы с 15+ строками и мелким текстом светлый фон даёт лучший контраст при длительном чтении и меньше «жжёт» глаза при типичном офисном освещении.

## 3. Как показаны direct / created / derived

Ключевое ограничение из спеки: «различия не должны основываться только на цвете» (§16). Решение — три независимых канала на каждый тип изменения, зафиксированные в одном месте (`CHANGE_META`, `components/ChangeMarker.tsx`):

1. **Цвет** — янтарь / тил / синий (direct / created / derived);
2. **Форма/иконка** — карандаш / плюс / стрелка-обновление, дублируются на маркере в таблице, на баре, в легенде и в badge модалки;
3. **Текстовый label** — «Изменено» / «Новая» / «Пересчитано», всегда рядом с иконкой в местах, где есть пространство;
4. Дополнительно для `derived` — диагональная штриховка бара, потому что это самый частый и потенциально самый «шумный» тип (в каноническом сценарии — 12 задач из 18), и его нужно визуально приглушить, а не выделить: только пересчитанные даты, никаких смысловых изменений полей.

Подсветка **сохраняется до следующей AI-команды** (а не сбрасывается по клику/закрытию модалки) — это единственный способ ответить на вопрос «что вообще произошло за последнюю команду», который PM задаёт себе, читая план уже после ответа AI. Ручной тумблер «Скрыть/Показать выделение» в легенде добавлен как escape hatch — посмотреть план «как есть», без визуального шума — но не как способ подтвердить/отклонить изменения (в MVP undo нет, это explicit out-of-scope, §4 спеки).

## 4. Как визуализируется изменение release date

Это выделено как «один из ключевых WOW-элементов demo» — и получило собственную визуальную трактовку, отдельную от обычных `ProjectMetric`:

- в строке метрик над Gantt — старая дата зачёркнута, новая — акцентным (янтарным, тем же, что `direct`) цветом, плюс явная дельта-плашка «+5 рабочих дней»; вся метрика получает подсвеченный фон-плашку, а не просто текст — это единственная метрика, которая имеет фон, поэтому глаз сразу цепляется именно за неё;
- то же самое (в упрощённом виде) повторяется в `ChangeSummary` внутри чата — release impact вынесен **над** секциями «Изменено/Добавлено/Пересчитано», а не после них, потому что это самый важный вывод из всей AI-команды и не должен требовать скролла, чтобы его увидеть.

Повтор одного и того же сообщения в двух местах (Gantt-метрики и чат) — намеренная избыточность, а не недосмотр: PM может увидеть релиз-импакт, не читая ответ AI целиком, если он смотрит на план, а не на чат в момент получения ответа.

## 5. Почему high-density интерфейс

Спецификация прямо описывает продукт как «рабочий PM-инструмент», а не marketing/onboarding-поверхность, и explicitly запрещает карточки на каждую задачу, большие paddings и лишние nested containers. Строка Гантта — 32px (не 40–48px, как в «воздушных» списках) — это осознанный компромисс: при 16–18 задачах план должен помещаться на экран без вертикального скролла, потому что именно целостный обзор плана — то, ради чего открывают инструмент. Как только видно всё сразу, пропадает необходимость держать в голове состояние прокрутки во время диалога с AI.

## 6. Собственный Gantt вместо библиотеки

На этом этапе сознательно не выбрана production-библиотека диаграмм — вместо этого лёгкий рендерер на React + CSS + SVG, изолированный в `features/gantt/` за модельным слоем (`ganttModel.ts` строит колонки/строки/связи из Project DTO, `ganttGeometry.ts` — чистые функции геометрии SVG, без React). Причины:

- на этапе high-fidelity prototype неизвестен финальный объём функциональности (drag-and-drop, critical path и т.д. явно out-of-scope MVP, но могут появиться позже) — рано фиксировать зависимость от конкретной библиотеки с её собственной моделью данных;
- изоляция модели (`GanttModel`) от компонента рендера означает, что переход на библиотеку в будущем — это замена **одного** файла (`GanttView.tsx`), а не переписывание workspace, chat-интеграции или change-подсветки;
- рабочих дней (Mon–Fri) в колонках — не календарных: выходные не получают колонку, а обозначены разрывом недели. Это уменьшает горизонтальную ширину диаграммы на ~28% и не тратит место на заведомо пустые дни — в доменной модели продукта нет понятия «работа в выходной».

## 7. Компромиссы, принятые для MVP-прототипа

- **Нет реального AI/backend.** Все ответы чата — детерминированная классификация текста сообщения (`features/chat/scenarios.ts`) поверх единственного реального перехода состояния в fixtures (`before` → `after`). Это осознанно: цель этапа — форма и поведение интерфейса, а не интеграция.
- **Даты не пересчитываются на фронтенде.** Все даты приходят «как есть» из fixture JSON — фронтенд их только форматирует и раскладывает по колонкам. Смена `Дата начала проекта` на Import screen не пересчитывает план (в проде это делает Scheduler на бэкенде).
- **Import validation — эвристика по имени файла**, а не парсинг реального `.xlsx` — потому что Excel I/O прямо вне scope этого этапа. Реальные данные (16→18 задач, конкретные ошибки) — из product-spec, а не сгенерированы случайно.
- **Export не создаёт файл** — только имитирует состояние `Готовим Excel… → Excel обновлён` на самой кнопке в хедере, без отдельного toast/панели — потому что в проде именно кнопка экспорта единственное, что должно менять состояние во время операции.
